Architecture & Mechanism · security review pipeline

cosmo.

A Claude-Code-based security review and zero-day discovery tool. The whole system is one function — run_review(target, config) → Report — wrapped in a handful of safety invariants that hold by construction. Every trigger calls that function; every network touch crosses one guarded broker; every public emission passes one fail-closed gate. It reuses Claude Code's auth/session/ tool-use — it does not fork it.

01

The review pipeline

One entry point serves every trigger — the CLI, the git hook, the GitHub Action, an interactive session, and the Claude Code plugin all call run_review. Findings flow through fixed stages in a fixed order: cheap static analysis first (its output handed to the model so it doesn't re-derive it), then the LLM stage, then any custom detectors, then the noise-control and prioritization stages, and finally a severity floor.

02

One guarded egress chokepoint

Nothing in cosmo opens its own socket. The four subsystems that touch the network — sandbox provisioning, authorized external recon, coordinated disclosure, and the model provider API — all route through a single broker, each tagged with a mode. The broker runs the same checks in the same order for every request, and re-checks every redirect hop against the same policy, so a redirect can't smuggle a request to an out-of-scope host.

03

Config trust tiers

The cosmo.yaml that ships inside a repo under review is untrusted — the code being scanned should never be able to relax its own review. Config merges under two rules: preference keys (threshold, ignore-paths, providers) let the repo override the operator, but safety keys (sandbox, fuzzing, external-targets, disclosure, extensions…) are operator-only and a repo value may only ever tighten them. A loosening value is clamped back and a warning is surfaced to the operator.

04

06

Extending it without forking

A researcher ships an extension — a Python module contributing any of a detector, a skill, or an /x-* command. Extensions are discovered from operator paths and installed entry points, but only activated when the operator lists them in the safety-tier extensions.enabled. Discovery and activation are a real boundary: a disabled extension's module is never even imported.

07

Relationship to Claude Code

cosmo does not fork Claude Code. It reuses its auth, session, and tool-use by shelling to the same cosmo binary from every surface — the CLI, the git hook, the Action, an interactive REPL, and the plugin. Enforcement therefore lives in exactly one place, and no surface can reach around it. Two roles for an LLM are kept separate: the model that reviews the code (the config-driven provider layer — Claude, Codex, DeepSeek, local Llama, ensemble) and the harness that drives the loop.

  • Your review model is your choice. The plugin is just a host surface; the model that finds bugs is set in providers: and is never forced to Claude — only the data-sensitivity gate can veto an off-box vendor.
  • Orchestration is model-agnostic too. Option 2 ships as cosmo agent: cosmo's own agent loop, where any planner — a local Llama, DeepSeek, or no model at all — proposes commands and the driver executes only through the guarded dispatch. The orchestrating model is contained to the exact surface a human at the REPL has.
  • One binary, many triggers. The plugin's /cosmo-* commands and the git hook both call run_review; there is no second, less-guarded path.
  • The plugin surface is generated, not hand-kept. cosmo plugin sync derives the commands from the guarded registry; cosmo plugin check fails CI on drift, so the plugin can never expose more than the enforced layer.
  • Graceful degradation. Importing cosmo never requires Claude Code or an API key — without them, the LLM stage is reported as skipped:, not silently passed.
